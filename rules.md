# DevPilot — Engineering & AI Rules

**Last updated:** 2026-09-28

> Rules any contributor or coding agent must follow. Read this + [architecture.md](architecture.md) + [phases.md](phases.md) before changing code. The deeper security rationale is in [docs/SECURITY.md](docs/SECURITY.md); the full agent context is in [docs/AGENT_CONTEXT.md](docs/AGENT_CONTEXT.md).

---

## 1. Before you code
- Inspect the actual checkout and `git status` — **docs may lag reality**.
- Work in small vertical slices; finish the current phase before advancing (see [phases.md](phases.md)).
- State exact file paths and the working directory for commands.
- Never claim a check passed unless it was actually run; report real results.

## 2. What to use
- **Python 3.11+**, FastAPI, Pydantic v2 (`model_dump`, `ConfigDict(from_attributes=True)`).
- **SQLAlchemy 2** typed mappings (`Mapped`, `mapped_column`).
- **Alembic** for every schema change; inspect autogenerated migrations before applying.
- Routes under `/api/v1` with explicit `response_model` and full type hints.
- Timezone-aware timestamps (`DateTime(timezone=True)`).
- Dependency injection via `Annotated[...]` aliases (e.g. `DbSession` in `app/api/deps.py`).
- Ruff for lint + format (config in `pyproject.toml`).

## 3. What to avoid
- ❌ Exposing ORM models as request bodies (use schemas).
- ❌ Business logic in routers (put it in services).
- ❌ `create_all()` as an app-startup migration substitute.
- ❌ Destructive DB commands without verifying the database identity first.
- ❌ Committing `.env`, keys, tokens, or generated artifacts (`.venv`, `*.egg-info`, caches).
- ❌ Broad `except:` that swallows errors or leaks internals to clients.
- ❌ Premature microservices, Kubernetes, Redis, or abstractions "for ceremony".
- ❌ Repository abstractions unless they give real isolation/query encapsulation.

## 4. Error handling
- Validate all input at the schema boundary; let Pydantic return `422` for bad payloads.
- Use precise `HTTPException` status codes: `404` not-found, `403` forbidden (Phase 3), `409` conflict, etc.
- Return safe error messages — never leak stack traces, SQL, secrets, or internal paths.
- Catch narrowly; re-raise or map to an HTTP error deliberately.
- Wrap multi-step writes in a transaction; let the service own commit/rollback.
- Log enough to debug, but redact secrets, full source, prompts, and diffs by default.

## 5. Database
- PostgreSQL is the source of truth. Keep **test and dev databases separate** (`devpilot_test`).
- Import ORM models into Alembic metadata so autogenerate sees them.
- Review every migration diff before committing; migrations are code.

## 6. Bounding the AI (guardrails)
- **Untrusted by default:** model output, repository/issue content, tool output, build/test logs, and prompts from repos. Treat repository prompt-injection as hostile; it must not change tool permissions or policy.
- **Provider-neutral:** no vendor lock-in in core business logic; provider + model are configuration.
- **Structured outputs:** prefer structured/typed outputs for plans and tool arguments.
- **Server-side authorization:** a model can never grant itself a permission or tool. Every tool needs a typed schema, explicit permission, server-side auth check, timeout, output limit, and audit record.
- **Bounded everything:** cap retries, timeouts, context size, and cost per run. Persist run status/events/state for resumption.
- **No secrets in the loop:** never place keys/tokens in prompts, logs, traces, or artifacts.
- **Sandbox untrusted code:** repository code runs only in a disposable, resource-limited Docker sandbox with network off by default; never mount the Docker socket or host secrets.
- **Human approval before publishing:** bind approval to the exact diff/artifact hash + base commit; invalidate stale approvals; record approver, decision, timestamp.

## 7. Definition of done
A change is done when: behavior implemented → input validated → tests + lint/format run and passing → docs updated ([memory.md](memory.md) at minimum) → secrets excluded → diff reviewed. No empty commits.

## 8. Testing rules
- Cover happy path, validation, not-found, authorization (Phase 3+), and failure paths.
- Integration tests use a **dedicated test database**; destructive setup never touches dev/prod.
- Mock live LLM/GitHub calls in normal CI; keep live tests opt-in.
