# DevPilot — Coding Agent Context

Read this file and the README, architecture, roadmap, progress, API, and security docs before changing code.

## Product definition
DevPilot is a human-supervised AI software engineering workflow: task/issue intake → repository inspection → structured plan → patch generation → isolated validation → human review/approval → GitHub PR. It is a workflow product, not just a chat wrapper.

**Do not confuse the target design with implemented functionality.** At this checkpoint, the confirmed implementation is an early FastAPI/PostgreSQL backend with a Project CRUD API.

## Architecture boundaries
- Router: HTTP, dependency injection, status codes, serialization; keep thin.
- Schema: validate input and define output; don't expose ORM models as request bodies.
- Service: use-case logic and transaction coordination.
- Model: persistence representation.
- Integration adapter: narrow wrapper around external provider.
- Agent node: bounded workflow stage; no ambient access to all tools.
- Sandbox: executes untrusted repository code, never the API host.

Use `router → schema → service → SQLAlchemy → PostgreSQL`. Do not add repository abstractions purely for ceremony; add them when they provide meaningful isolation or query encapsulation.

## Coding conventions
- Python 3.11+; follow Ruff settings.
- SQLAlchemy 2 typed mappings (`Mapped`, `mapped_column`).
- Pydantic v2 (`model_dump`, `ConfigDict(from_attributes=True)`).
- Keep routes under `/api/v1`, use explicit response models and type hints.
- Use timezone-aware timestamps.
- Avoid broad exception swallowing and leaking internals.
- Keep `.env`, credentials, tokens, and generated local artifacts out of Git.

## Database rules
- PostgreSQL is the persistent source of truth.
- Use Alembic for schema changes; inspect autogenerated migrations.
- Import ORM models into Alembic metadata.
- Do not use `create_all()` as an application startup migration substitute.
- Never run destructive commands without verifying database identity.
- Keep test and development databases separate.

## Agent/model rules
- Provider abstraction; no vendor lock-in in core business logic.
- Prefer structured outputs for plans and tool arguments.
- Persist run status, important events, and state needed for resumption.
- Bound retries, timeouts, context, and cost.
- Model output and repository/issue content are untrusted.
- Tool authorization is server-side; a model cannot grant itself permission.
- Never expose secrets in prompts, logs, traces, or artifacts.

## GitHub and sandbox rules
- Keep credentials server-side and use least privilege.
- Bind a run to repository, base branch, and base commit SHA.
- Execute repository code only in a disposable, resource-limited sandbox.
- Disable network by default; never mount the Docker socket or host secrets into untrusted execution.
- Require explicit approval before publishing; bind approval to the reviewed diff and base commit.

## Tests and definition of done
Test happy paths, validation, not-found, authorization, and failure paths. Mock live LLM/GitHub calls in normal CI. Integration tests must use a dedicated test DB.

A feature is done when behavior is implemented, errors validated, tests/checks run, docs updated, secrets excluded, and the diff reviewed. Report only checks actually run and their true results.

## Working style
The user is building incrementally and wants to understand the work. Give exact paths for every file, state the working directory for commands, and use small checkpoints. Finish the current phase before jumping ahead.
